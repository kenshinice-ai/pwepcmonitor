# PWE PC Monitor v0.7.2 Review 与优化方案

审查日期：2026-09-26  
基线：`v0.7.2` / `5fffe84ac96cfe48de15b65feebfb53e95fa26c7`

## 1. 结论与范围

下一轮建议优先修正**读数归属、不可用状态和窗口生命周期**，再做悬浮窗细节打磨。当前最重要的问题不是增加展示内容，而是保证显示的数值来自正确设备、缺失数据不被当作零、隐藏的悬浮窗不会被后台操作重新展开。

本轮仅审查和编写方案，不修改产品代码，不提交、不发布。保留现有深蓝半透明、金色翅膀、紧凑态图标与数值、悬停详情，以及“不可用内容隐藏，原因进入设置”的产品规则。不加入风扇控制、驱动替换或新的监控功能。

验证边界：已完成相关代码静态检查；macOS 上 Release 构建通过，0 warnings、0 errors；`git diff --check` 通过。未执行 Windows WPF 实机交互、驱动和多显示器验证。以下明确区分代码可确认的问题与需要实机复现的风险；构建成功不代表这些运行时场景通过。

## 3. 具体发现与最小修复方案

### R01 — 统一存储设备身份

**证据：** [SystemSampler.cs](../src/Pwe.PcMonitor/Services/SystemSampler.cs#L53) 使用硬件枚举得到的存储名称，但容量来自基础采样；同文件约第 143 行保留第一个存储名称，第 212–213 行逐个覆盖吞吐量，温度最终取所有硬盘的最大值。[WindowsMetricsReader.cs](../src/Pwe.PcMonitor/Services/WindowsMetricsReader.cs#L84) 的容量则来自系统盘根目录。

**影响：** 多硬盘机器可能同时展示 A 盘名称、系统卷容量、B 盘速率和最热硬盘温度。它们即使分别真实，组合起来也具有误导性。

**方案：** 为同一卡片建立明确的设备/卷归属。优先保持系统卷容量及卷标签；只有能可靠关联的硬件名称、温度和速率才进入该卡片。无法映射的读数不猜测、不拼接，诊断中保留来源。不要为了本次修复引入复杂磁盘管理界面。

**验收：** 两块硬盘使用不同名称、容量、速率和温度，交换枚举顺序后卡片归属不变；无法映射时不显示错配字段。

### R02 — GPU 温度校验必须贯穿到最终快照

**证据：** [GpuTemperatureProvider.cs](../src/Pwe.PcMonitor/Services/GpuTemperatureProvider.cs#L81) 对候选温度做范围筛选，但 [SystemSampler.cs](../src/Pwe.PcMonitor/Services/SystemSampler.cs#L248) 使用 `gpuTemperature.Temperature ?? Max(gpuTemps)` 回退到未经过相同筛选的原始集合。提供器仍允许仅有热点或显存温度时将其选为最终值。

**影响：** 被过滤的异常温度可能重新进入 UI；用户不能区分核心、热点和显存温度。多 GPU 还存在按名称分组、负载与温度分别聚合的身份歧义，应明确当前聚合含义。

**方案：** 删除绕过校验的回退；统一验证有限数值、合理范围和传感器类型。通用 GPU 温度优先使用核心/边缘读数；只有次级传感器时不得静默冒充核心，放入明确标注类型的诊断信息。设备关联优先使用稳定标识，不以显示名称作为唯一身份。

**验收：** 覆盖空集合、NaN、Infinity、超范围读数、仅 hotspot、仅 memory、核心与热点并存、两张同型号 GPU；任何无效数据均不能重新进入最终快照。

### R03 — 分离“零”“未知”“过期”

**证据：** [SystemSampler.cs](../src/Pwe.PcMonitor/Services/SystemSampler.cs#L75) 异常时返回新建快照；[Readings.cs](../src/Pwe.PcMonitor/Models/Readings.cs#L23) 的非空 CPU 数值默认零、时间戳默认当前时间；[MonitorViewModel.cs](../src/Pwe.PcMonitor/ViewModels/MonitorViewModel.cs#L66) 始终格式化 CPU 数值。基础 CPU 读取失败同样返回零。GPU/功耗历史还将缺失值通过 `?? 0` 写成零。

**影响：** 采样失败可能显示 CPU 0%，缺失区间成为真实曲线中的零值，容易被理解为机器正常空闲。

**方案：** 明确采样成功、字段可用和最后成功时间；失败不能更新为“刚采到的零”。沿用现有隐藏规则，诊断放设置；如保留上次有效值，必须限制保留时间并明确过期状态。历史序列保留缺口，不注入假零。CPU 首次采样作为基线初始化处理。

**验收：** 模拟基础读取失败、完整采样异常、首次启动、单项掉线和恢复；缺失值不显示为零，不绘制虚假的下降曲线，恢复后自动显示。

### R04 — 等待采样停止后再释放硬件资源

**证据：** [MonitorViewModel.cs](../src/Pwe.PcMonitor/ViewModels/MonitorViewModel.cs#L178) 启动采样任务但未保存；采样循环使用 `Task.Run`，而同文件约第 423 行的 `Dispose` 取消后立即释放采样器。[SystemSampler.cs](../src/Pwe.PcMonitor/Services/SystemSampler.cs#L495) 随即关闭硬件对象。取消令牌不能直接中止已经执行中的同步采样代码。

**风险：** 退出、重启或重新检查传感器时，硬件更新与关闭可能重叠；退出阶段仍可能安排 UI 更新。本轮没有复现崩溃，不能将风险写成已发生的故障。

**方案：** 保存采样任务，建立停止采样→等待完成→关闭硬件对象的顺序；派发 UI 更新前检查关闭状态。退出路径异步等待，不在 UI 线程同步阻塞等待依赖 Dispatcher 的任务。

**验收：** 用可控的慢采样器模拟退出，确认 Close 不早于 Sample 完成；Windows 连续启动/退出及重检传感器，无未处理异常和退出后更新。

### R05 — 隐藏悬浮窗时完整关闭详情状态

**证据：** [App.xaml.cs](../src/Pwe.PcMonitor/App.xaml.cs#L306) 直接调用悬浮窗 `Hide()`；[FloatingWindow.xaml.cs](../src/Pwe.PcMonitor/FloatingWindow.xaml.cs#L55) 的计时器/Popup 清理依赖 Closing；同文件约第 185 行在内存操作开始时直接展开详情，未检查悬浮窗是否可见或启用。

**风险：** 主窗口发起内存整理可能触发隐藏悬浮窗的详情展开路径；悬停中关闭悬浮窗时 Popup 与内部标记可能未一起复位。实际显示结果需 Windows 验证。

**方案：** 提供统一隐藏入口，关闭 Popup、停止计时器并重置指针/展开标记；内存操作只维持已经可见的悬浮窗详情，不唤醒被关闭的悬浮窗。保持原产品行为：点击其他位置收起托盘面板，不自动隐藏悬浮窗。

**验收：** 关闭悬浮窗后从主窗口整理内存；详情展开时从托盘关闭悬浮窗；整理进行中关闭并重新启用。三种情况都无残留详情、无意外重新显示。

### R06 — 内存整理保护用户正在使用的应用

**证据：** [MemoryOptimizer.cs](../src/Pwe.PcMonitor/Services/MemoryOptimizer.cs#L32) 在动作开始时才读取前台 PID。若用户先激活主窗口再点击，前台已是 PWE，原工作应用不再被这条规则保护。候选只保存 PID 与工作集，在之后打开进程时未复核启动身份。现有实现已有进程数量限制和受保护进程列表，应保留。

**方案：** 明确定义“原前台应用”并在进入应用操作前保留其身份；执行前再次检查当前前台与候选身份，防止进程退出/PID 复用导致误选。当前筛选实际按会话，不应仅凭会话号宣称验证了用户所有权。结果使用“估算工作集减少”等准确措辞，不承诺同等数量的可用物理内存或系统加速。不增加待机缓存清空、后台自动整理等动作。

**验收：** 原工作应用被排除；候选退出或身份变化时跳过；权限不足允许部分成功且反馈准确；连续点击不会启动并行整理；完成结果有足够阅读时间。

### R07 — 网络速率基线绑定适配器

**证据：** [WindowsMetricsReader.cs](../src/Pwe.PcMonitor/Services/WindowsMetricsReader.cs#L98) 按累计流量挑选活动网卡，但收发基线只有一组，未绑定网卡 ID。

**影响：** Wi-Fi/以太网切换时，可能用新网卡计数减旧网卡计数，产生异常峰值或零；累计流量最高也不一定是当前主要使用的接口。

**方案：** 按稳定适配器 ID 保存或重置基线；切换、断线、计数回退时重新预热。明确网卡选择规则，至少保持当前有效接口，避免因历史累计量变化而频繁跳动。

**验收：** 覆盖网卡 A→B、断开重连、计数回退及首次采样；切换不出现由跨设备相减产生的尖峰。

### R08 — 紧凑态图标、数值与颜色使用同一选择结果

**证据：** [MonitorViewModel.cs](../src/Pwe.PcMonitor/ViewModels/MonitorViewModel.cs#L75) 标签/数值优先级是 GPU→电池→功耗，但第 89 行健康色选择为 GPU→功耗→Calm，跳过了电池。

**影响：** 没有 GPU、同时有电池与功耗时，电池百分比可能呈现功耗健康色。

**方案：** 从同一个已选指标派生图标、数值、副标题和颜色；电池沿用现有中性策略，不顺便引入新告警规则。

**验收：** 以 GPU/电池/功耗的有无组合做表驱动检查，各字段始终指向同一指标。

### R09 — 冒烟测试验证成功里程碑，而不只是“还活着”

**证据：** [build.yml](../.github/workflows/build.yml#L39) 启动后等待固定时间，仅在进程已退出且退出码非零时失败；仍存活的进程会被结束并视为通过。日志存在时复制，但没有断言初始化与有效采样完成。

**影响：** 卡死、被对话框阻挡或未完成采样的进程可能通过发布检查。现有 CI 不能作为视觉或交互验证证据。

**方案：** 输出明确的初始化完成、基础采样成功、正常退出里程碑；超时应失败并保留日志。将无硬件依赖的选择/格式化/状态逻辑加入小型自动化测试。驱动读取与 WPF 交互保留单独的 Windows 实机清单，不要求无桌面的 CI 假装完成视觉验证。

**验收：** 正常、故意抛错、故意挂起、无采样结果四种模式中，仅正常模式通过；失败日志可直接定位阶段。

## 4. 悬浮窗设计微调：先验证，再做局部修改

不再增加紧凑态信息密度，不重做品牌。以下是待验证项，不是本轮已经复现的缺陷：

- **键盘与焦点：** 详情收起判断应考虑键盘焦点；焦点仍在详情按钮内时不能仅因鼠标离开而收起。验证 Tab、Enter、Escape，以及现有内存快捷键的实际作用范围，不将窗口级快捷键宣传成全局快捷键。
- **单位与可访问名称：** GPU 时钟紧凑显示的 `0.4G` 应在完整标签、Tooltip 和可访问名称中说明 GHz。图标按钮要有动作名称，颜色不作为唯一状态提示。
- **混合 DPI：** 在 100%、150%、200% 缩放及左右/上下排列显示器上验证边缘展开、拖动和工作区限制；当前坐标换算是否跨屏正确需实机判断。
- **结果可读性：** 内存整理完成后，反馈不应因短收起延迟而来不及阅读；优先调整现有状态持续时间与 Tooltip，不新增常驻大面积信息。
- **系统偏好：** 已有减少动画处理应保留；检查浅/深主题、系统高对比度和透明背景下文字辨识度。优先修具体不清晰场景，不引入额外主题框架。

位置持久化、多 GPU 独立详情、更多自定义指标属于可选后续需求，不纳入本轮最小修复范围。

## 7. 本轮交付与限制

本轮产出为审查方案，未修复以上问题。已经运行的验证仅证明当前基线可构建且无差异格式错误；硬件兼容性、退出竞争及 Popup 实际行为仍需按清单验证。建议先完成第一、二阶段再发布，避免只改外观而保留数据语义和窗口状态问题。
